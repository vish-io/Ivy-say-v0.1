# Windows acceptance checklist

Use a test Groq account and non-sensitive sample text. Automated tests cover WAV, Ogg encoding, chunk logic and mocked provider requests, not OS integration or the live provider. Check current Groq model availability and costs before testing.

1. Build, run tests, and publish using the README commands. Launch the published app on a clean Windows 10/11 account with microphone permission enabled.
2. First launch opens settings. Save a valid key, close and reopen the app, and verify dictation works; confirm `groq.key` is ciphertext and contains no plaintext key. Replace and remove the key; restarting after removal should show settings. Check that another Windows account cannot decrypt the first account's key.
3. Focus Notepad; press Ctrl+Win+Space, speak, and press it again. Check output for default prose and for Code, Email, and Bullet prefixes. Exercise punctuation, Unicode, multiline output, fast repeated shortcuts and very short or silent recordings.
4. Test both models and disable polishing. Confirm disabled polish returns raw transcript and does not interpret spoken mode prefixes. Check observed timings over a range of utterances and network conditions; do not assume a fixed latency.
5. Focus another window while processing. Verify nothing is injected into it and the recovery window shows the output. Change focus during a long insertion and verify the partial-insertion warning. Copy manually and check the target before pasting.
6. Exercise invalid key, network disconnect, provider rejection and formatter failure. Verify errors reveal neither keys nor response bodies; formatting failure should insert the raw transcript if the original target is still focused, and display a warning in the pill. Check that no audio or transcript files were written.
7. Select a microphone in settings and verify it is the one being recorded. Disconnect the selected device and verify Ivy Say reports it unavailable instead of using a different device. Deny microphone permission, remove/disconnect the device, and test unsupported microphone formats. Confirm a useful error and that a subsequent valid attempt works. Check automatic stop at 115 seconds and maximum memory protection.
8. Occupy the hotkey with another app before launching, open a second Ivy Say instance, and test quitting while idle, recording, and processing. Verify no lingering microphone capture or process. Test standard and elevated targets, multiple monitors, DPI scaling and screen-reader access.
9. Review unsigned binaries, dependencies, update/distribution plan, privacy policy, provider terms, threat model and accessibility with your release team before deploying to users.

## Language and recognition checks

Test auto-detect and the selected spoken-language setting with the same phrase, including short clips and background noise. Compare the raw Whisper transcript to the AI output, and test Hindi and Punjabi only with appropriate speech. Check a name without hints and with an optional spelling hint; then clear the hint and verify it is no longer included. Inspect a synthetic multipart request in automated tests for the correct language and hint fields. Manually confirm non-sensitive hints are saved locally and transmitted to Groq, and review the output for invented name changes. Mixed-language speech and low-volume audio can still be misrecognized.

## Personalization checks

Use non-sensitive invented terms. Save vocabulary and a correction like `grindel wald => Grindelwald`, enable personalization, and confirm the comparison shows Whisper, local correction, and formatter output separately. Verify rules match whole phrases case-insensitively without replacing substrings or applying a second rule to already replaced text. Disable and save; verify no personal hints or corrections are used. Re-enable, restart, and confirm the profile survives. Delete data and verify it is gone after restart. Inspect `%LOCALAPPDATA%\IvySay\personalization.dat` for ciphertext, not the sample terms. Exercise unreadable/corrupt profile, duplicate rules, empty fields, and long hints. Test accents with representative recordings and measure accuracy and latency; no training occurs.

## Insertion and provider security

Use only harmless sample text. Check normal one-line dictation in Notepad remains automatic. In level 1 (Guarded), check multi-line and tabbed output and a known Windows Terminal window show a review window without typing. In level 2 verify every dictation is held for review. In level 0 verify these checks do not force review, using harmless samples and a safe test environment; focus and injection errors can still prevent insertion. Verify copying is explicit, and that control characters cannot be automatically typed or copied in levels 1 and 2; level 0 does not block them. Check target/focus switches during processing and insertion; confirm warnings and verify potential partial output. Test IDE integrated terminals, browsers, remote desktop, password fields and elevated applications: detection is incomplete, so level 2 is recommended. Automated tests use mock HTTP responses for oversized responses, unexpected finish reasons, and insertion policy; they are not a live provider or Windows UI test.

## Streaming output

With a test Groq key and harmless dictations, verify default preview shows fragments in the pill, then inserts only once after completion. Test both levels 1 and 2 with multiline results and verify their review rules still apply. With level 0 and direct streaming enabled, use Notepad and check fragments appear incrementally, in order, without duplicate final insertion. Switch focus and disconnect the network after typing begins: verify no raw transcript is automatically inserted and the recovery window warns about already-inserted partial text. Test an error before the first fragment and the raw fallback, a long dictation, Unicode, Code/Bullet output, and optional comparison. Measure time-to-first-visible-text and total latency separately. Automated tests simulate server-sent events; they don't test live Groq, actual Windows focus behavior or partial insertion.

## First-word latency and WPM

Use a test key. Check the pill shows “Done in …s” after an AI-formatted result, measured from starting the AI request to successful SendInput of the first completed word, not recording or Whisper time. Compare the streamed first AI fragment timing in the comparison window: it measures a different event and can be lower. Try preview and direct-streaming modes, a single word, a focus change, formatting failure and AI disabled; no AI-first-word time should be reported if no formatted text was inserted. SendInput indicates Windows accepted input events, not that the application rendered them.

In My words, check the seven-day figure after multiple successfully inserted dictations of known word counts and audio duration. Verify weighted total words / total recording minutes, today plus six previous local calendar days, no count for review-only or partial failures, persistence after restart, and Clear stats. Inspect the stats file for aggregate counts and durations only, no transcription text. Check Unicode, punctuation, code, and no-speech behavior. Unit tests exercise the timer and daily aggregation, not actual OS insertion or live-provider timings.

## Formatter fallback

Automated mock tests simulate 429/503 and an interrupted stream on the primary, successful 120B fallback, errors from both models, bad credentials, cancellation and partial direct insertion. Manually with an authorized test account, verify 20B is selected for ordinary short speech, and 120B is selected for a long dictation or a supported explicit English correction cue. Test threshold boundaries, disabled smart selection, and comparison-window model/reason reporting. Verify both 20B-to-120B and 120B-to-20B fallback paths. If safe and feasible, use a controlled network/provider stub to simulate eligible failures: preview should clear before switching to 120B; a direct stream that has already typed any text must not retry or insert raw text. Check model indication, latency including both attempts, failure messaging, and account-specific quota/cost behavior. Compare quality and latency over identical raw transcripts; routing accuracy and model quality are not established by mock tests. Never share API keys or transcript data in test logs.

## Long dictations and compression

Use non-sensitive speech and a test key. Test below and above the configured threshold, at 8 seconds and at 14 seconds, with chunking on and off and each compression setting. Inspect the comparison window for chunked/full/retry labels, and check that recording-time uploads happen only when chunking is enabled and the threshold has been reached. Test sustained speech with no pauses, pauses at boundaries, repeated phrases, numbers, names, mixed languages, silence and very short tails. Compare transcripts against manually corrected references and the full WAV baseline. Simulate an empty, failed or ambiguous chunk and ensure a full uncompressed retry occurs; cancellation must not retry. Test closing the app and losing the network mid-recording. Confirm audio remains in memory and no files are created. Live recognition quality, quota use, latency, microphone operation and focus/insertion require Windows and a real account.

## Capture integrity and restart diagnosis

Wait for Listening, then dictate a known phrase and play back the original audio in the comparison window. Repeat after reboot and a microphone reconnect, changing the Windows default device, and with an explicitly selected device. Verify the selected source, timing, words and playback level; a visible level does not establish that speech is intelligible. Check identical-name devices fail safely rather than silently selecting the first. Test muted and disconnected inputs, low-volume speech, constant DC, noisy silence and clipped speech. Nearly flat audio should be rejected without typing a Whisper hallucination; noisy silence is not guaranteed to be detected. Test closing comparison during playback, app shutdown during capture startup, and empty/failed chunk handling. With compression off and chunking disabled, use non-sensitive speech to compare captured playback against the raw Whisper transcript for both models and language settings, before and after reboot. Automated PCM and HTTP tests cannot validate actual Windows devices or Groq recognition.

## Simplified settings navigation

On a clean account, verify General shows the key input expanded and the user can save a key, choose a language, microphone, shortcut, AI polish and insertion safety mode. On an existing account, check the key section is collapsed but can be expanded to replace or remove the key. Verify My words saves separately and the global Save settings button is hidden on that tab; General and Advanced use the same Save settings button. For every advanced setting, select a non-default value, save, close and reopen; verify the value remains unchanged. Save a General-only change and verify it does not reset hidden Advanced values or personal words. Test all three safety levels and direct typing warning; retain the privacy notices and checks. Check the shortcut restart message appears when the shortcut changes. Test scroll, keyboard navigation, focus, high-DPI scaling, narrow windows and maximized windows.

## Animated pill

On Windows, confirm the orb is visible in the pill, rotates and cycles colors continuously without blocking the status text, drag area, or settings button. Test idle, recording, processing, errors and completion, hotkeys while another application is focused, settings open/close, multiple DPI scales, window drag and app exit. Check the animation and glow on a low-powered machine and remote desktop. The native WPF blur/color treatment approximates CSS filter contrast/hue-rotation; visual fidelity and actual performance require an interactive Windows test.
